# M6.3 — Controlled revalidation and recovery: report

Status: **hypothesis PARTIALLY SUPPORTED (pre-registered rule, clause 3).** M6.3 is complete as an implementation and measurement milestone. The revalidation protocol is **safe** (0–1 false restorations in 400 must-not-restore streams), restores **far more, far faster and without exposing users** than M6.2's probe-based recovery, and is the only mechanism that ever restores a structurally invalidated or stale cell — but it is **uneconomical in the benchmark world as frozen**: it spends 0.3–2.5M tokens per stream to recover a benefit worth about 0.145 utility per restored decision, so its pooled net utility is *below* M6.2's by a margin whose confidence interval excludes zero. Nothing was promoted, no default changed, and M7 was not touched. Source artefacts: [audit](../research/m6_3_revalidation_audit.md), [frozen design](../experiments/revalidation-design.md), [generated tables](./revalidation-tables.md), [ADR 0018](../decisions/0018-controlled-revalidation.md), operating guide [controller.md](../controller.md).

All simulation results are on **synthetic** streams with known ground truth (the M6.2 worlds plus five new scenarios); the real-model section is a single exploratory case. Every number below is generated by `ee-ctl reval-sim` / `reval-report` from the stored per-stream results (a held-out run of 6,000 stream results; repeated, §14) and is reproducible by command.

## 2. What changed relative to M6.2 (audit, summarised)

The audit ([m6_3_revalidation_audit.md](../research/m6_3_revalidation_audit.md)) traced the M6.2 lifecycle and found, before any M6.3 code existed: a recovery criterion whose single look passes a *fully recovered* world only 34–41 % of the time (F1); structural invalidation and stale evidence unrecoverable **by construction** (35 recovery attempts, 0 recoveries on S8; 0 attempts on S8b) (F2, F3); recovery evidence taken from user traffic, with ~100 production probes per episode (F4); the quarantine reason not carried into recovery (F5); no lineage (F6); no verification-availability concept (F7); no budget beyond probe counts (F8); and a timer — not evidence — opening recovery (L8). M6.3 addresses F2–F8 directly; F1 is replaced by an exact-error test.

## 3. The design as built (frozen before any data)

Full text: [revalidation-design.md](../experiments/revalidation-design.md); operating summary: [controller.md](../controller.md#controlled-revalidation-of-quarantined-cells-m63).

* **Layering, not rewriting.** The M6.2 `advance` machine, `DriftParams`, the overlay schema and every stored M6/M6.1/M6.2 hash are untouched (pinned by a 185-test compatibility set that was re-run after every change). Revalidation is a second machine per quarantine episode; it disables native recovery through the existing `locked` flag. A new `ControllerParams.revalidation` block is omitted from the serialised form when unset, and revalidation changes no decision until a cell is quarantined (tested on the simulated controller). Two additive helpers on `MonitorFleet` (`restore`, `replace_reference`) are the only edits to M6.2 code.
* **Reasons by projection** of the existing `DriftTrigger` (no duplicated enum values beyond the spec's names). **Eligibility** is a gate list with one reason per failed gate. **States** `QUARANTINED → REVALIDATION_PENDING → REVALIDATING → RECOVERY_CANDIDATE → RECOVERED`, plus `EXPIRED` and `BUDGET_EXHAUSTED`. **Strategies** A (fixed exact test), B (A's test behind an evidence-readiness gate), C (SPRT, truncated), one statistical hypothesis for all (success not worse than the reference by ≥ 0.10, exact binomial error control, plus a cost guard). **Verification**: five verdicts; only an explicit pass is a success; unavailable verdicts consume budget and are never evidence. **Lineage** on every trial and transition. **Persistence**: migration 0008, two append-only tables, exact replay with prefix verification.
* **Protocol corrections (design §10, both before any held-out data, both found by a 3-seed development smoke run, both applied to all strategies equally).** E1 *cost futility*: a cycle stops early with a failure when the lower bound of mean trial tokens exceeds the guard (it can only veto, never recover); in S4 it cut cost per stream from 3.0M to 0.44M tokens. E2 *trial throughput*: one trial per simulated hour made a 200-trial test occupy 200 of an 800-decision stream; changed to 50 trials per 10-hour round (12 simulated minutes per trial). **Time-to-restoration results are bounded by this assumption.**

## 4. Experiment protocol (summary)

Variants on identical streams with common random numbers: `m61` (coarse guard), `m62` (M6.2 ENFORCE, native probe recovery), `m62_locked` (permanent quarantine), `m63_A/B/C`. Ten scenarios of 800 decisions, onset 250: *should restore* — S5 temporary disturbance, S8 runtime change (performance unchanged), S8b stale evidence, R3 common-cause outage (both arms degrade), R4 disturbance plus a revalidation-verifier outage over [380,600), R5 relapse; *must not restore* — S2 persistent collapse, S4 persistent cost drift, R1 residual degradation (15.6-point drop after a partial recovery), R2 structural change plus degradation. Ground truth is the perturbation's *performance* degradation (a runtime relabelling alone is structural). Seeds: development 110000–110199 (smoke and exploratory only), audit-exploration 7100000–7100011 and all M6.2 seeds excluded, **held-out 9000000–9000099**. Acceptance criteria (a)–(h) and the verdict rule were frozen with the design; the report code (`revalidation_report.py`) implements them and is tested on synthetic results that force each verdict branch.

## 6. Safety

False restoration over the four must-not-restore scenarios: A 1/400, B 1/400, C 0/400. The single A/B event is an R1 stream (a 15.6-point residual drop, near the 10-point margin): the exact test's size is bounded by α = 0.025–0.05 *given the estimated reference*, and the reference itself carries ±0.03 sampling error, so a small non-zero rate is expected near the boundary. The more severe the degradation, the smaller the risk: S2, S4 and R2 are 0/300 for every strategy. The M6.2 native rule, which was not designed with an error bound, false-restored **5/100 R1 streams** (exact upper bound 10.2 %): its fixed-threshold look has no size guarantee, and the audit's F1 showed it passes a true 7-point drop 12 % of the time per look.

R5 (relapse) is the one scenario where a *correct* restoration is followed by harm: after the world degrades again at position 550, A/B restored 64 % (3 % of streams restored during the relapse) and C 72 % (5 %); users see up to +50 more degraded decisions than under permanent quarantine until the monitor re-detects (C: 116.9 vs 66.3 degraded decisions per stream). The M6.2 monitor re-arms and re-quarantines (`episode` 2), so the relapse is bounded, not prevented.

## 7. Recovery power and speed

Restored by the end of the stream and median delay from the end of the disturbance (decisions; [IQR]):

| scenario | m62 native | A | B | C |
|---|---|---|---|---|
| S5 temporary disturbance | 51 %, 305 [240, 350] | 79 %, 80 [60, 170] | 79 % | **84 %, 80 [50, 140]** |
| R3 common-cause outage | 44 %, 276 [235, 321] | 82 %, 90 [60, 180] | 82 % | **83 %, 100 [50, 150]** |
| R4 outage of the revalidation verifier | 37 %, 290 [231, 317] | **59 %**, 270 [260, 300] | 59 % | 55 %, 270 [250, 290] |
| R5 relapse | 3 % (all false) | 64 % | 64 % | 72 % |

**Negative result — R4.** While the revalidation verifier is down (positions 380–600) every trial is `VERIFICATION_UNAVAILABLE`; the unverified-fraction rule correctly ends each such cycle without a restoration, but each ended cycle **counts as a failed cycle**, so three cycles are consumed during one outage and the case ends `BUDGET_EXHAUSTED` before the verifier returns (40/100 C streams). A verification outage is not evidence about the capability; the design conflates them. This is the reason criterion (b) fails for every strategy (55–59 % vs 70 %), and the fix (retry without consuming a cycle, expire on a separate TTL) is a design change for M6.4, not something to tune after seeing the data.

**The remaining non-restorations** (12–16 % in S5/R3) are `BUDGET_EXHAUSTED`: a cycle fails by chance in about a quarter of healthy worlds (exact power at the planned effect ≈ 0.73–0.80 given the reference's sampling error), a failed cycle is followed by a cooldown (100 decisions after a severe failure), and three failed cycles or the 3M-token lifetime budget end the episode. A truncated SPRT is also inconclusive when the true success lies between the two hypotheses.

## 8. Structural invalidation and stale evidence

M6.2 treated a runtime change (S8) and stale evidence (S8b) as quarantine reasons that **cannot recover** (audit F2, F3) and measured the cost (+22–25 % tokens for −2 % successes against M6.1). Under M6.3: A/B restore 89 %, C 90 % in each; the structural case validates under the *new* runtime and rebases the reference's version labels (an event in the log), the stale case refreshes the evidence time. Successes per stream against the rule baseline: S8 C **+15.0** (native +6.8, permanent quarantine +6.3, M6.1 +18.0); S8b C +12.5 (native +6.3, M6.1 +18.0). M6.1's coarse guard — which never notices a runtime change — still wins on net utility in these two *harmless-change* scenarios (+117.5 vs C +47.5 / −2.6): the cost of M6.2's structural channel is reduced by revalidation but not removed, because proving compatibility is itself ≈ 1M tokens. R2 (structural change *and* degradation) is correctly refused 0/100 by every strategy.

## 9. Verification handling

All five verdicts exist and are tested; only an explicitly verified pass is a success (`classify_run_outcome`; a goal criterion that could not be evaluated yields `VERIFICATION_UNAVAILABLE`). In R4 the unavailable trials cost tokens (20.6 per stream), were never counted in n, and ended cycles. Over all 1,000 held-out streams there were **0** restorations resting on > 20 % unverified trials ((d), exact). **Lineage rejections never occurred in the simulations** (0 rejected trials; the simulated executor is lineage-clean); the four rejection reasons are exercised only by unit tests (and the real-orchestrator integration test). The reasons seen were `PERFORMANCE_DEGRADATION`, `COST_DEGRADATION`, `STRUCTURAL_INVALIDATION`, `EVIDENCE_STALE`; `STATISTICAL_DRIFT` (CUSUM), `VERIFICATION_FAILURE` and `UNKNOWN` were not exercised by the experiment.

## 10. Strategy comparison

* **C vs A.** C spends 45 % of A's tokens (ratio 0.45 [0.43, 0.47]) and restores at least as often in every should-restore scenario except R4 (55 vs 59 %), with the safest false-restoration count. The saving is largest where it matters most — a dead capability: S2 0.28M vs 2.55M tokens, R2 0.28M vs 2.29M — because the SPRT rejects after ≈ 14 trials per cycle where a fixed test runs all ≈ 199.
* **B vs A.** B was identical to A on 938/1,000 streams. Its readiness gate (the rule default's concurrent verified outcomes show a healthy environment) only matters in R3, where it did not change restoration. **B's added complexity is not justified by these results.**
* **Truncated SPRT.** C is inconclusive (BUDGET_EXHAUSTED) when the true success lies between the hypotheses; its worst case is the full 320 trials ≈ 2M tokens.

## 11. Economics

**Spend.** Revalidation tokens per stream (production tokens are in the tables): C — S5 1.08M, R3 1.10M, R4 0.83M, S8 0.97M, S8b 1.70M, R5 1.05M, and on must-not-restore cells S2 0.28M, R2 0.28M, R1 0.73M, S4 0.44M; A — 1.8M, 1.8M, 1.2M, 1.4M, 2.2M, 2.6M and 2.6M, 2.3M, 2.4M, 0.44M. S8b is the most expensive *should-restore* case because staleness recurs: the evidence ages out again every 250 simulated hours, so the cell is quarantined and revalidated repeatedly (C: 1.9 cases and 1.65 restorations per stream, against 1.0 case for permanent quarantine); **this recurring cost is the maintenance cost of keeping aged evidence in service** and is included in every figure.

**Net utility** (utility = verified successes − (production + revalidation tokens)/20,000, per stream, vs the rule baseline on the same stream; C vs M6.2 native): S5 +9.1 vs +38.9; R3 +22.7 vs +56.5; R4 −4.8 vs +38.2; S8 +47.5 vs +46.4; S8b −2.6 vs +40.0; pooled difference C − native **−29.7 [−33.6, −25.8]** (A −59.4, B −58.3); C vs permanent quarantine −21.1 [−25.1, −17.1]. Only where native recovery is impossible (S8) does C match it, and M6.1's coarse guard — which never quarantines a harmless runtime change — still wins there (+117.5).

**The price per additional verified success** (independent of the weight λ in the utility): against native recovery, C buys **+4.84 [4.01, 5.73] verified successes per stream** (S5 +5.5, R3 +3.6, R4 +0.8, S8 +8.2, S8b +6.2) at a net token cost of **+690k** (revalidation +1,137k, production −447k because a restored alternative is cheaper): **≈ 142k tokens per extra verified success** (A: +4.26 for +1,273k = 299k). A verified success must be worth ≥ 142k tokens — 7× the 20k assumed by the utility definition, about 22 trials' cost — for C to pay for itself against native recovery in this world.

**What the token utility does not show: user-facing exposure.** M6.2's native recovery sends 85–105 live probes per stream to the quarantined alternative; revalidation sends none. Relative to permanent quarantine, native recovery runs the *degraded* alternative on up to +56 more production decisions per stream (R1 +56, S2 +48, R2 +47, S4 +42; S5/R3/R4 +5), which is where its lost verified successes go (S2: −32.2 successes vs −16.1 for permanent quarantine and for revalidation). Revalidation moves that cost out of the user's path and into the learning plane — at a price paid in tokens.

**Break-even** (arithmetic on the measured costs, in the tables file): a restored alternative earns ≈ 0.145 utility per decision; C's ≈ 1M tokens (≈ 54 utility) therefore need ≈ 370 restored decisions to be repaid; streams of 800 decisions restore around position 480–600.

Given time, M6.2's slow native recovery restores almost every temporary disturbance (19–20/20) at negligible cost and remains ahead on net utility; revalidation still yields more verified successes (S5 +18.1 vs +14.9; R3 +32.0 vs +23.3) but at 1.3M tokens. ## 15. Limitations and negative / inconclusive results

1. **Synthetic worlds.** All simulated results are in worlds I specified: one family, an alternative that is 0.02 better on success and 28 % cheaper per token than the default, independent revalidation tasks drawn from the same distribution as production. Whether a real revalidation pool exists, is representative, and has a trusted independent verifier is the main unresolved question.
2. **Economics are world-dependent.** The benefit per restored decision (0.145) and the trial cost (6,500 tokens) are small and large respectively *relative to each other*; with a larger advantage or cheaper tests the sign changes (§11). The 800-decision horizon is an M6.2 modelling choice.
3. **Trial throughput is an assumption** (E2): time-to-restoration is not a property of the algorithm alone.
4. **The paired advantage is not retested.** Revalidation proves the alternative's own success level; the default's drift is seen only through its concurrent production outcomes (B's readiness gate, which did not matter).
5. **Reference uncertainty.** Error guarantees hold relative to the *estimated* reference (n = 240); the realised false-restoration rate near the margin (R1) was 0–1 %, not zero.
6. **R4 design flaw** (§7): a verifier outage consumes failed cycles. **Confirmation** is a collapse guard only; its value was not isolated (the `confirm_trials=0` ablation is exploratory, §12). **Lineage rejections** and three reasons were never exercised by the experiment.
7. **Single-cell, single-tenant.** No pooled or multi-family monitors; no automatic capability retirement or regeneration; no latency channel.
8. **No live shadow or canary** of an M6.3 policy, and no real-model *acceptance* experiment: the real-model case (§13) is one exploratory case.
9. **No multiplicity correction** across the ten scenarios (descriptive tables; the pre-registered criteria are the pooled ones).
10. **Two of the brief's eligibility inputs are not gates.** *Evidence provenance*: whether the prior itself is production-eligible is checked when a policy is trained (M6.2 `assess_evidence`), not again at revalidation — restoring a cell does not make a research-only prior production-eligible (the definition's `prior_sources` record is unchanged), but revalidation will happily test one. *Evidence freshness as a gate*: stale evidence is a quarantine *reason* with its own protocol (the reference's evidence time is refreshed on recovery), and case age is bounded by the TTL; there is no separate "evidence is too old to revalidate" gate. Both belong in the M6.4 gate list.
11. **The `reval-real` command and `OrchestratorTrialSource` prefetch pool are exploratory tooling**: the former has no automated test beyond its parts (the source, the case machine and the verdict mapping are tested; the CLI wiring is not).

## 16. Conclusions and recommendation

* **Supported:** out-of-band, reason-aware, bounded and independently verified revalidation can restore quarantined cells *safely* (false restoration ≈ 0 where the world is clearly degraded), *faster* (≈ 4× sooner) and *without exposing users*, and it is the only mechanism that recovers structurally invalidated or stale evidence; sequential testing halves its cost at no loss of safety; every transition is explainable and replayable from persisted evidence.
* **Not supported:** that it is worth its cost *in this benchmark world* — rigorous recovery needs ≈ 150 verified trials per cycle, and the benefit of a restored alternative is too small to repay that inside 800 decisions. Nor that evidence-threshold readiness (B) adds anything, nor that a verifier outage can safely be treated as a failed cycle.
* **Do next (M6.4), in this order:** (1) separate *verification-unavailable* from *criteria-not-met* (retry without consuming a cycle); (2) an **economic eligibility gate** — revalidate only when the expected benefit over a stated horizon exceeds the expected trial cost, and report the horizon; (3) cheaper tests (a wider margin for compatibility-only cases, early cost/safety vetoes, shared trials across cells); (4) a live **shadow** run of an M6.3 policy and a revalidation pool from real verified tasks, then a canary of an `ENFORCE` revalidation policy through the existing offline → shadow → canary gates; (5) a real-model acceptance experiment (the exploratory case here is not one). Do not adopt B; do not tune the frozen parameters on the held-out seeds.
